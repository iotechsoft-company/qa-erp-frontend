# Business workflow coverage

อัปเดตเมื่อ 2026-11-15 เทียบ [Workflow & API Sequence Guide](https://iots1.github.io/plan-erp/api-workflow-guide.html) กับ Purchasing baseline ใน [PR #3](https://github.com/iotechsoft-company/qa-erp-frontend/pull/3) (review fixes `c037770`, merge commit `ebcb6a7`) และ P0.2 บน `codex/purchasing-receiving` ที่รอ review ขอบเขตใหม่ระบุในแถว A2/A3; เอกสาร baseline มาจาก PR #4 ที่ merge แล้วเป็น `0737711` และ healthy Sales create migration แยกใน [PR #5](https://github.com/iotechsoft-company/qa-erp-frontend/pull/5) ตาม deployed fix

คู่มือมีตัวเลขสรุป 21/23 flows ไม่ตรงกับเนื้อหาที่เพิ่มภายหลัง เอกสารนี้จึงแจกแจง **25 รหัสหลัก A1–A5, B1–B5, C1–C10, D1–D2, E1–E3** และหัวข้อย่อยทั้งหมด รวม C9 ที่ไม่มีในตาราง Overview ด้วย ไม่มีการคิดเปอร์เซ็นต์จากจำนวนเทสหรือ endpoint

## วิธีอ่านสถานะ

- **ทำแล้ว** = มี assertion ใน spec สำหรับขอบเขตที่ระบุ ไม่ได้หมายถึง flow ทั้งหมดเสร็จ
- **บางส่วน** = มี happy path/validation บางขั้น แต่ยังขาดผลข้างเคียงหรือทางเลือก
- **ยังขาด** = ยังไม่มี assertion สำหรับพฤติกรรมนั้น การเปิด route ได้หรือใช้ API เป็น setup/cleanup ไม่นับเป็น workflow coverage
- **บั๊กขวาง** = มี issue และ regression ยืนยันอาการเฉพาะ; เทสผ่านเมื่อยังพบอาการนั้น ไม่ใช่ healthy flow ผ่าน
- **quarantined** = `test.fixme` ไม่ได้รัน; ห้ามนับเป็น coverage ที่ผ่าน

UI/API ในตารางหมายถึงขั้นที่มี assertion จริง ผล stock/บัญชีระบุแยกในคอลัมน์เดียวกันเพื่อลดการตีความเกินหลักฐาน Issue ทั้งเก้ารายการด้านล่างยัง OPEN ใน GitHub metadata เมื่อเช็ก แต่ frontend#3/#4 มี deployed fix จาก frontend PR #1 และ healthy regressions แล้ว (ดู B1–B3); issue annotation ไม่ได้แปลว่ายังถูกบล็อกเสมอ ผลรันเดิมเป็น baseline ของเอกสาร; การเพิ่ม P0.2 Receiving และผลตรวจใหม่แยกไว้ใน ROADMAP

## เกณฑ์ปิดหนึ่ง flow

ครบเส้นทางปกติและทางเลือกที่ระบุในคู่มือ, state/validation/permissions, stock/เงิน/บัญชีที่เกี่ยวข้อง, cancel/reversal/dependency guards พร้อมหลักฐาน spec และผลรันซ้ำตามกฎ repo จึงปิด flow ได้ การใช้ API seed ต้องระบุขอบเขตชัดเจน; API workaround, bug characterization หรือ fixme ไม่ทำให้ full UI flow เสร็จ

ลำดับลงมือและ dependency อยู่ใน [ROADMAP — Business workflow priorities](ROADMAP.md#business-workflow-priorities-2026-11-15) เมื่อเพิ่ม/แก้ spec ให้ปรับทั้ง matrix และ roadmap พร้อมกัน ประวัติผลรันเก่าใน ROADMAP เป็นหลักฐานตามวันที่ ไม่ใช่ผลรันใหม่หรือเปอร์เซ็นต์ความครอบคลุม
